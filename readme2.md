# Автотесты PomidorQA

Набор автотестов на PomidorQA — сервис 25-минутных встреч для QA/IT-специалистов: регистрация, профиль с навыками, слоты доступности, каталог участников, бронирование и отмена встречи.

Продукт тестируется как чёрный ящик: исходного кода приложения у набора нет, доступен только живой стенд `https://aiqa.su`. Поэтому покрытие считается от функциональных требований, а не от строк кода.

## Что проверяет проект
Основной бизнес-риск продукта — встреча, о которой договорились два человека. Она не должна теряться, дублироваться и доставаться двоим одновременно. Вокруг этого построен набор:

* **Сквозной путь:** «зарегистрировался → заполнил профиль → открыл слот → нашёл в каталоге → забронировал → увидел встречу у обоих участников»;
* **Гонка за один слот:** два одновременных запроса на один и тот же промежуток времени — подтверждённой остаётся ровно одна бронь, второй участник видит понятную ошибку;
* **Освобождение слота после отмены:** встреча удаляется из ближайших, переходит в отменённые, а слот становится доступен для повторного бронирования;
* **Границы роли:** гость видит хоста в каталоге, его навыки и доступное время, но при попытке бронирования получает требование войти в аккаунт. Приватные страницы перенаправляют гостя на форму входа.

## Архитектура
* `tests/unit/` — чистые функции набора — без сети и браузера (валидация паролей, пересечение слотов);
* `tests/api/` — бизнес-правила и HTTP-контракт — без UI (бронирование, проверки ограничений на бэкенде);
* `tests/e2e/` — пользовательские сценарии в браузере (каталог, логика отмены, часовые пояса);
* `tests/helpers/` — генерация тестовых данных, Arrange через API и автоматический cleanup сессий;
* `tests/pages/` — Page Object: локаторы и действия конкретных экранов системы.

Разделение жёсткое: в spec — сценарий и проверки, в helper — данные пользователя, в Page Object — экран. Локаторов в spec нет, expect в Page Object нет.

Уровень выбирается по риску, а не по привычке: правила брони дешевле проверять запросом, а не кликами, поэтому они живут на API-уровне. UI отвечает за то, что человек реально видит на странице.

> **Оговорка про пирамиду:** unit-уровень во внешней автоматизации проверяет собственный код набора (файл `src/pyramid/slots.ts`), а не продукт. Широкое основание пирамиды здесь недостижимо, и это осознанный компромисс, а не недоработка.

## Как запустить
```bash
npm ci
npx playwright install --with-deps chromium

npx playwright test                 # Запуск всех 33 тестов
npx playwright test --project=unit  # Только unit-тесты
npx playwright test --project=api   # Только API-тесты
npx playwright test --project=e2e   # Только E2E-сценарии в браузере
```

Стенд по умолчанию — продакшен (`https://aiqa.su`). Переопределяется переменной окружения:
```bash
POMIDORQA_BASE_URL=http://localhost:3000 npx playwright test
```

## Что проверяет CI
В GitHub Actions настроен автоматический пайплайн на каждый Pull Request:
1. **Typecheck and lint** — проверка типов TypeScript и правил стабильности из `eslint.config.mjs`. Браузер не поднимается, пока статика красная.
2. **Playwright tests** — параллельный прогон unit, API и E2E тестов в headless-режиме на Chromium.
3. **Отчёты** — выгрузка HTML-отчёта с трейсами упавших шагов в артефакты сборки.

## Известные дефекты
Расхождения требований и продукта не спрятаны ради искусственно «зелёного» отчёта. Тесты на них написаны строго по ТЗ и помечены `test.fail()`:

| ID | Требование | Что происходит на самом деле | Тест |
|---|---|---|---|
| **KD-3** | R8.3: Каталог фильтрует только по навыкам «могу помочь» | Фильтр каталога ошибочно ищет по всем навыкам. Поиск находит тех, кто указал навык в блоке «хочу разобрать». | `e2e/skill-search.spec.ts` |

Пока дефект жив в продукте, ожидаемый результат теста — падение, и общий прогон остаётся зелёным. Когда баг починят на бэкенде, Playwright сообщит `expected to fail, but passed` — это будет сигналом снять пометку.

## Личный вклад
* На основе предоставленных заготовок полностью адаптировал проект под свой личный репозиторий, устранив расхождения в путях и архитектуре хелперов;
* Интегрировал сквозной сценарий гостевого доступа без регистрации (`e2e/guest-access.spec.ts`), проверив ограничения приватных страниц и валидацию формы авторизации при попытке забронировать слот;
* Настроил автотест для валидации часовых поясов (`e2e/slot-timezone.spec.ts`), контролирующий корректность отображения локального времени слота для хоста и гостя;
* Перевёл очистку тестовых сред на автоматический трекер контекстов браузера (`contextTracker.cleanup()`), полностью исключив появление «мусорных» данных между прогонами;
* Сформировал финальную матрицу покрытия требований MVP и свёл фактические метрики прогона (`33 тестов`) в единый инженерный отчёт.
